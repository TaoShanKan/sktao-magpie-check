# SDD 索引

这里采用 Specification-Driven Development：先明确可观察行为和验收，再实施、验证并维护规格。它是项目内部工作约定，不依赖额外脚手架工具。

## 目录约定

一个能力一个目录：`specs/<feature>/`，使用以下文件：

- `spec.md`：目标、边界、编号需求及状态。
- `plan.md`：实现方案、接口变化与兼容考虑。
- `tasks.md`：可检查的实施和验证任务。
- `contracts/acceptance.md`：需求对应的验收场景、证据及未验证项。

新目录按 [模板](TEMPLATE.md) 创建。修改同一能力时直接维护已有规格；独立能力再建目录，并登记本索引。

## 工作流

1. **规格**：记录用户目标、可观察行为、失败场景和范围；关键未决问题明确标注，已明确的部分继续推进。
2. **方案**：定位代码拥有者，确定最小接口及持久化变化；涉及历史数据时说明迁移或保留方式。
3. **实施**：按任务清单落实；需求改变时同步规格，避免只修改计划。
4. **验证**：逐条记录验收结果，关联实际测试或手工证据；失败、未执行、环境限制单独记录。
5. **归档知识**：把长期有用的结构、接口及排查入口整理到知识库，规格保留功能承诺和验收结果。

实施状态使用「草案／实施中／已实现／已替代」；验收场景使用「通过／失败／未执行」。自动验证通过不自动等于用户验收通过。基线规格是对已有实现的回填，`plan.md` 描述既有设计，`tasks.md` 按实际交付登记。

最新用户要求优先。代码证明当前行为，规格描述预期行为；发现二者不一致时记录差异并处理，不能仅通过改文档掩盖实现缺陷。
